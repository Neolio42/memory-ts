PATTERN: UIInputViewController with child view swap — normal keyboard view replaced by recording overlay on mic tap, restored after transcription.

COMPONENTS:
- KeyboardViewController (UIInputViewController): owns state machine, manages child view lifecycle, inserts text via textDocumentProxy
- KeyboardView: full QWERTY + numbers/symbols pages, UIStackViews + UIButtons, shift/capslock via time-based double-tap detection, long-press delete repeating timer
- RecordingOverlayView: animated waveform bars (CADisplayLink with weak proxy), recording/processing/error states, stop button
- KeyboardTranscriptionService: orchestrates KeyboardAudioCaptureService → WebSocketClient, callback-based, session UUID guards against stale callbacks
- KeyboardAudioCaptureService: NOT singleton, AVAudioEngine, 16kHz mono Int16 PCM, exposes audioLevel (os_unfair_lock protected), handles interruptions
- KeyboardState: enum with transition validation via canTransition(to:)

KEY DESIGN CHOICES:
- Callback-based (not Combine/async) — keyboard extensions have tight memory budgets
- Not a singleton for audio — extensions get killed and recreated
- Session UUID guards prevent stale transcript insertion
- Backpressure: drops audio chunks when >5 in-flight
- KeyboardConstants.appGroupSuite = "group.com.whisnap.app" (shared constant)

WHY:
- Extensions capped at ~50MB — Combine + async overhead avoided
- Keyboard extensions are frequently init/deinit'd — singletons cause zombie state

REJECTED: SwiftUI-based keyboard (no direct UITextDocumentProxy access), Combine publishers (overhead), singleton audio engine (lifetime mismatch)
