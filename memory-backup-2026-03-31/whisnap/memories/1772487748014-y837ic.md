DECISION: Replace sherpa-rs ONNX CPU backend with FluidAudio Swift SDK for CoreML acceleration

OPTIONS CONSIDERED:
- Keep sherpa-rs CPU (3-5x RTF, works today, Rust-native)
- FluidAudio Swift SDK via C FFI (110x RTF, macOS 14+/Apple Silicon only, Swift-only SDK)
- ONNX CoreML EP (broken for transducer models, sherpa-onnx issue #2910)

REASONING:
- 110x RTF = 60 seconds of audio in ~0.5 seconds on M4 Pro — orders of magnitude beyond requirement
- FluidInference had to rewrite TDT decoding in Swift because CoreML can't express the token prediction loop as a graph — this is why ONNX CoreML EP fails for transducers
- 50,000+ monthly downloads, used in VoiceInk/Spokenly/Slipbox — production-proven
- v3 model = 25 European languages (vs v2 English-only)
- FluidAudio SDK handles HuggingFace model downloading itself, but we pass custom model path to load from our managed directory
- Input: 16kHz mono Float32 PCM — exact same format we already produce
- macOS 14+ / iOS 17+ on Apple Silicon — acceptable constraint for Whisnap

MODEL: FluidInference/parakeet-tdt-0.6b-v3-coreml (~2.67GB)
- Contains: Encoder.mlmodelc, MelSpectrogram.mlmodelc, Joiner.mlmodelc, PredictionNetwork.mlmodelc, etc.
- Each .mlmodelc has nested weights/ subdirectory with weight.bin files

SWIFT INTEGRATION PATTERN:
- NOT a sidecar process — static C FFI like FoundationModelsWrapper and FnKeyHelper
- Swift package with @_cdecl exports → linked at build time
- Rust calls via extern "C" declarations in a fluid_audio_ffi.rs bridge

REVISIT WHEN: Cross-platform support needed (Windows/Linux) — then sherpa-rs fallback path
