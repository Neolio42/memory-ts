PRINCIPLE: Cloud sync schema versioning requires no explicit versioning mechanism when you follow this rule: server always deploys before desktop client ships.

HOW TO HANDLE EACH SCENARIO:
- Adding a new field: Add to server allowlist first → deploy → then update desktop to send it. Old desktop = just doesn't send it → user gets default. No problem.
- Old clients sending unknown fields: Server DROPS silently (log warning, no 400, no storage). Old client doesn't break, just doesn't sync that field.
- Removing a field: Stop reading it in desktop. Leave in server allowlist forever (costs nothing). It becomes inert.
- Never remove from allowlist, only add.

WHY PASSTHROUGH FELT USEFUL: Avoided the need to coordinate server+client deployments. But the actual cost was a DB full of garbage with no way to distinguish real settings from leaked implementation details.

THE REAL COORDINATION NEEDED: Just add a string to an array and deploy before shipping desktop update. That's it.

NOTE: This is distinct from the strict 400 for unexpected fields during the clean-up phase - once the system is clean, unknown fields from old clients should be silently dropped, not errored, to preserve backward compatibility.
